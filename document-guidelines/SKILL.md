# Document Guidelines

Use plain language by default. Write for the intended reader and assume they may be new to the project or use English as a second language. Use familiar words, active voice, and short sentences. Use the same term for the same thing. Keep precise technical terms where they help, and explain unfamiliar terms on first use.

- Validate documented behavior, commands, and paths against the project. Keep the facts and rationale a maintainer will need later. Update the relevant section in place.
- Keep session history, debugging notes, and validation logs in a separate work log. Track work logs only when requested or required by the project.
- Write procedures in execution order. Include prerequisites and permissions that affect success. Use copy-pasteable commands and put required edits in clearly named variables or separate steps.
- Explain significant side effects before the step that causes them. Show how to verify success when the outcome is hard to see.
